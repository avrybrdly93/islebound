# 40 — Decision Log

Append-only record of architecturally or design-significant decisions: what was decided, the alternatives, and why. Referenced from other docs as `DECISION_LOG NNNN`. When an agent or human is tempted to relitigate a choice, the answer starts here.

**Format:**

```markdown
## NNNN — Title (YYYY-MM-DD)
**Status:** accepted | superseded by NNNN | rejected-idea
**Context:** the situation and forces at play
**Decision:** what we chose
**Alternatives:** what we did not choose, and the honest cost of our choice
**Consequences:** what this commits us to
```

## 0001 — Simulation separated from presentation, deterministic and headless (pre-dev)
**Status:** accepted
**Context:** AI-agent-driven development needs machine-verifiable gameplay; multiplayer needs server-side rules; saves need serialisable truth.
**Decision:** `sim/` is pure (no three.js/DOM/`Math.random`/wall-clock), fixed 30 Hz, intent-in/event-out, hashable. Enforced by lint + CI.
**Alternatives:** game state on three.js objects (fast to start, unhashable, untestable, unnetworkable); 60 Hz sim (2× CPU for no perceptible gain with interpolation).
**Consequences:** one indirection per entity per frame; every feature designed as intents/events; the single most protected invariant in the repo.

## 0002 — Multiplayer designed from day 1, implemented in Phase 7
**Status:** accepted
**Context:** retrofitting networking onto a single-player architecture is the standard death of projects this shape; but building netcode first starves the game of content for a year.
**Decision:** the `36` §4 network-safe checklist applies to every Phase 1–6 feature; the server reuses `sim/` verbatim; transport is swapped, not the game.
**Alternatives:** MP-first (momentum death); SP-only then rewrite (architecture death); lockstep (Rapier non-determinism, late-join cost).
**Consequences:** mild ongoing tax on every feature review; Phase 7 becomes an integration project instead of a rewrite.

## 0003 — Client–server authoritative; no P2P, no lockstep
**Status:** accepted — see `36` §2 for the full argument.
**Consequences:** we operate a server (`38`); the cost envelope must stay hobby-scale.

## 0004 — Content is data (`as const satisfies` TS tables), no runtime schema library
**Status:** accepted
**Context:** content must scale without code changes; zod et al. add a dependency to validate data we author in TS and already type-check.
**Decision:** typed const tables + hand-written guards only at untrusted boundaries (saves, network).
**Alternatives:** JSON + zod (runtime cost, dependency, worse editor support); a CMS (absurd at this scale).
**Consequences:** content edits are code PRs (fine — they get CI); guards must be maintained by hand at the two boundaries.

## 0005 — Rapier3D, used narrowly; physics excluded from the authoritative hash
**Status:** accepted
**Context:** hand-rolling a character controller is weeks of bug-tail; but Rapier is not bit-deterministic across architectures.
**Decision:** Rapier for collision + character controller + ≤40 dynamic bodies; gameplay outcomes never depend on precise physics; positions quantised (1 cm) for save/wire; server physics is truth in MP.
**Alternatives:** cannon-es (unmaintained), ammo (huge), custom (expensive), full determinism via fixed-point (enormous cost for a co-op builder).
**Consequences:** `worldHash()` covers game rules, not float transforms; the desync test asserts gameplay-state equality only.

## 0006 — One authored island, guided generation, pinned seed
**Status:** accepted
**Context:** procedural-infinite conflicts with "a place you know"; pure hand-modelling is a different (larger) project.
**Decision:** 512 m island from control map + seed `0x48414C43`; landmarks hand-placed; everyone plays the same island.
**Alternatives:** per-player seeds (kills shared conversation, multiplies QA surface); multiple islands (post-1.0 at most).
**Consequences:** worldgen changes need the generator-version migration path (`23` §5); the island can be *learned*, which the whole design leans on.

## 0007 — Gravity −18 m/s², not −9.81
**Status:** accepted
**Context:** real gravity at our character scale and jump height reads as floaty and slow.
**Decision:** −18 with a 1.15 m fixed jump, coyote 0.12 s, buffer 0.12 s.
**Consequences:** all airborne tuning derives from this; changing it invalidates the movement checklist results.

## 0008 — No tool durability
**Status:** accepted
**Context:** durability creates maintenance chores and inventory anxiety; its pacing function is already served by tool *tiers*.
**Alternatives:** slow durability with cheap repair (still a chore, just a small one).
**Consequences:** tools are one-time crafts; progression pressure lives entirely in gates and recipes.

## 0009 — No crop quality tiers; crops never die
**Status:** accepted
**Context:** quality tiers add min-max pressure without feeling; withering punishes absence, violating C2.
**Consequences:** farming's ceiling is expression and cooking variety, not optimisation — accepted deliberately.

## 0010 — No free terrain digging; foundations flatten only
**Status:** accepted
**Context:** free terraforming breaks the authored silhouette, complicates colliders/streaming, and bloats saves.
**Decision:** the only terrain edit is foundation flattening with restore-on-removal (`13` §7).
**Alternatives:** voxel or heightmap brush editing (a different, much larger game).
**Consequences:** building expression is additive (structures) rather than subtractive; save stays tiny.

## 0011 — No structural integrity; "if it snaps, it stands"; no cascade on removal
**Status:** accepted
**Context:** integrity simulation punishes experimentation and produces the least-cozy moment possible (your house collapsing).
**Consequences:** floating pieces are legal; the art direction absorbs it (chunky style reads as intentional).

## 0012 — 100% refund on removal, always
**Status:** accepted — cozy contract C6; property-tested (T2).
**Consequences:** no material sink from building; economy pressure must never be balanced against refunds.

## 0013 — Recipe discovery is legible (unlock rules), not experimental
**Status:** accepted
**Context:** combine-to-discover is charming but opaque; it violates the Legibility value when a player misses core recipes.
**Consequences:** the unlock graph is the de-facto quest system and is reachability-tested (T7).

## 0014 — Weather is deterministic from (seed, day, hour)
**Status:** accepted
**Context:** determinism gives free multiplayer agreement, free offline catch-up honesty, and testability.
**Alternatives:** random weather synced over the wire (state to sync, histories to reconcile).
**Consequences:** weather cannot react to player actions (acceptable — no design wanted it to).

## 0015 — Sleep fast-forwards time (200×), never jumps
**Status:** accepted
**Context:** a jump requires bespoke catch-up logic per system, which drifts from real behaviour.
**Decision:** sleeping runs the actual simulation quickly; T9 asserts hash-equality with playing through.
**Consequences:** systems must be efficient at large tick throughput (bucketing everywhere) — a constraint that also bought us fast offline catch-up.

## 0016 — JSON+gzip saves in IndexedDB; verify-before-promote; rolling backups
**Status:** accepted — see `23` §2–4 for the argument (debuggability over bytes at these sizes).
**Consequences:** revisit binary only if saves exceed 5 MB.

## 0017 — React DOM overlay for UI; per-frame HUD on a 2D canvas; no state library
**Status:** accepted
**Context:** DOM UI is accessible and agent-writable; React must never run per frame.
**Alternatives:** in-engine UI (accessibility cost, huge effort), zustand/redux (unneeded for ~10 tiny stores).
**Consequences:** the store pattern (`24` §1) is the only sanctioned UI state mechanism.

## 0018 — Cloudflare Pages + Fly.io; not Vercel Hobby
**Status:** accepted
**Context:** Vercel's Hobby tier prohibits commercial use; Pages permits it with unlimited bandwidth; Fly gives cheap regional VMs with volumes for SQLite.
**Consequences:** deployment tooling targets these two; the cost envelope in `38` §8 depends on them.

## 0019 — Hand-rolled binary protocol; content indices on the wire
**Status:** accepted
**Context:** the message set is small; codecs double as DoS bounds-checking; protobuf/msgpack add dependency and schema tooling for no gain here.
**Consequences:** every wire change bumps `PROTOCOL_VERSION` and maintains the N−1 codec for 7 days.

## 0020 — No accounts, no analytics, no global social surface at 1.0
**Status:** accepted
**Context:** accounts are the largest security/scope cliff available; behavioural analytics conflicts with the project's stance; public social spaces require moderation staffing.
**Consequences:** cross-device saves are manual export/import at 1.0; the harassment surface is structurally near zero.

## 0021 — Subdomain hosting, not a subpath under avesstudios.com
**Status:** accepted
**Context:** the intended URL was `avesstudios.com/islebound`, but avesstudios.com is hosted on Vercel/Netlify. Cloudflare Pages attaches custom domains at a hostname, never a path, so a subpath requires proxying the game through the main site's host.
**Decision:** the game is served from `islebound.avesstudios.com` (a CNAME to Cloudflare Pages). `avesstudios.com/islebound` becomes a landing page on the existing site with a Play link.
**Alternatives:** proxying via Vercel/Netlify rewrites (throws away Cloudflare's unlimited bandwidth — the reason it was chosen in `30` §1 — and re-inherits Vercel Hobby's commercial-use prohibition; ~6,500 first-loads/month before the 100 GB free cap); moving DNS to Cloudflare plus a Worker on `avesstudios.com/islebound*` (works, but adds a moving part to a one-person operator's incident surface for a cosmetic URL).
**Consequences:** the game gets its own origin, so IndexedDB saves cannot be squeezed out of quota by anything else deployed under avesstudios.com — which matters given how much of `23` exists to protect saves. Marketing URL and artefact URL differ.

## 0022 — Trunk-based development, single environment
**Status:** accepted
**Context:** `30` was originally written with staging and production tiers, which suits a launched game with players. There are no players until 1.0, and the operator is one person.
**Decision:** `main` is production, deployed on every merge. No staging tier, no tag-triggered deploys. Tags mark phase completions as records only. PRs on `phase-N/*` branches retain the CI gate and per-PR preview URLs.
**Alternatives:** keeping two Pages projects (a second environment to maintain and reason about, for a benefit that does not exist pre-launch).
**Consequences:** nothing catches a change that passes CI and the smoke test but is subtly wrong until it is live — acceptable with no players, not acceptable after 1.0. Mitigations are the blocking Playwright smoke test and Cloudflare's instant rollback. **Revisit at 1.0**: adding a `release` branch and a second Pages project is cheap then and is in the Icebox.

## 0023 — "Allocates nothing" is measured by call-site attribution, not by heap growth (2026-08-13)
**Status:** accepted
**Context:** `06` §"no allocation in per-frame paths" is an enforced rule, so it needs a measurement, and BL-004's acceptance criterion asks for one. Inferring it from process-wide heap growth over a loop works at whole-process resolution and fails at per-operation resolution: the figure is a process quantity divided by one operation's iteration count, so any other allocation during the loop is charged to the operation. Measured consequence — three to five of thirty allocation-free operations read exactly one returned object's worth of bytes, and the set changed when unrelated parts of the test file changed.
**Decision:** allocation is measured with V8's sampling heap profiler (`HeapProfiler.startSampling` via `node:inspector`), summing bytes attributed to the measuring loop and its callees, and the pass threshold is derived from a deliberate-allocator control measured **in the same process and run** rather than written as a constant.
**Alternatives:** `heapUsed` before/after delta (measures retention, not garbage — under-reported a control sevenfold); `PerformanceObserver` on `'gc'` (reports zero collections for 200k provable allocations on Node v22.22.2); one child process per measurement (would work, and costs a process spawn per operation — reconsider if the profiler ever regresses); waiting for Vitest under BL-015 (a guess that the runner was the problem; it was not).
**Consequences:** the reported figure is **not** bytes allocated — the profiler under-reports volume ~100× because young-generation allocation from optimised code takes a bump-pointer fast path it does not sample — so this instrument answers "allocates / does not" and must not be used for a byte budget. A future per-frame *budget* needs a different instrument. Two settings are load-bearing and both fail dangerously in one direction: too coarse a `samplingInterval` and too long a `warmup` each make the control itself read zero, which is why the control-derived threshold is not optional.

## 0024 — Query caches are invalidated by version counters, not by the tick boundary (2026-08-22)
**Status:** accepted
**Context:** `04` §4.3 asked for queries "cached per-tick by component-set signature", and BL-059's third acceptance criterion asked for a component added or removed *mid-tick* to be reflected rather than served stale. Those are not the same requirement, and a cache cleared once per tick — the obvious reading of the first — fails the second outright: inside a tick it is exactly the stale cache the criterion forbids. `04` §4.4's intent-in/event-out design makes mid-tick component churn the normal case rather than an exotic one; a `gather` intent removes a `ResourceNode` in the same tick a later system queries for it.
**Decision:** each cached result records the `version` of every `ComponentStore` it was computed from plus `EntityAllocator.version`, and is reused only while all of them still match. Store counters are bumped in exactly the places `sortedCache` is already cleared; the allocator's is bumped on `destroy` and deliberately not on `create`.
**Alternatives:** clearing the cache on the tick boundary (fails criterion 3, and throws away work 30 times a second when nothing changed); comparing `ComponentStore.size` and `EntityAllocator.liveCount` (both can return to a previous value — one add and one remove, or one create and one destroy, leave them unchanged while the set has changed); re-deriving the result and comparing (that is the work the cache exists to avoid).
**Consequences:** the cache is strictly fresher than the per-tick one `04` described and can never serve something it would not have, so nothing depending on the old wording can break; `04` §4.3 is amended to say so. The cost is two counters on classes that had none, and the standing obligation that any future mutating method on `ComponentStore` bumps one — mitigated, not eliminated, by putting the bump on the same lines as the existing `sortedCache` invalidation. **`create` not bumping the allocator's counter is a claim, not an omission**: a fresh entity has a component in no store, and a recycled index cannot inherit one because the dense array holds whole handles. `Query.test.ts` pins it. If a future change lets a newly created entity acquire components without a store `set` — a save-load path that populates dense arrays directly, say — that claim breaks and this counter must bump on `create` too.

## 0025 — A world's system list and its event map are one choice, not two (2026-08-23)
**Status:** accepted
**Context:** BL-061 assembles `World` from `EntityAllocator`, `ComponentRegistry`, `QueryCache` and `EventBus`. `04` §4.3 writes `events: EventBus` unparameterised, but `EventBus` is generic over an event map, and the map itself belongs to `sim/events/` — a later item. The natural shape was `World<M>` with the map defaulted, plus `SYSTEM_ORDER` imported directly as `step`'s system list. That does not compile, and the reason is structural rather than incidental: **`EventBus<M>` is invariant in `M`.** It holds a `Map<keyof M, Slot[]>` and an `on` whose handler parameter is `M[K]`, so `World<M>` is assignable to `World<M2>` for no other `M2` at all — not the empty map, not the widest one. A `System<M>` mentions `World<M>` in parameter position, so a system list is typed at one map and one map only.
**Decision:** `World<M>` keeps the type parameter, and takes its system list as a **constructor argument** rather than importing `SYSTEM_ORDER`. `SYSTEM_ORDER` is annotated at the map the game uses — `Record<never, never>` today, since no event type exists — and production wiring passes it explicitly. There is no setter and no `addSystem`.
**Alternatives:** casting `SYSTEM_ORDER` to `RegisteredSystem<M>[]` at the default parameter (sound only while the array is empty, which is a landmine for whoever adds the first system, and one nothing would catch); dropping the type parameter and typing the bus at `EventMap` (`keyof object` is `never`, so `emit` accepts nothing and the first real system has to undo the decision); declaring the event map in `sim/World.ts` (invents a later item's type in the wrong module, against `05`'s layout). Each of the three was tried against the typechecker rather than reasoned about — the third variance error, on `World<M>` → `World<never>`, is what settled it.
**Consequences:** the order stays data in `sim/systems/order.ts` exactly as `04` §4.3 requires; what changed is who reads it. Handing the world its order is the better shape independently of the type system — no module-level global reached for from inside a class, a test can run recording systems without touching the authoritative array, and a server and a client can share this class with different lists. The cost is that `new World(...)` now has a required argument, and that **when `sim/events/` lands, `SYSTEM_ORDER`'s annotation is the single place the map is named** — every `World` built from it follows by inference. A system list typed at a different map than its world is a compile error rather than a runtime surprise, which is the property worth having.

## 0026 — Destroying an entity removes its components eagerly, not on a sweep (2026-08-25)
**Status:** accepted
**Context:** BL-060. `World.destroyEntity` delegated to `EntityAllocator.destroy` and stopped, leaving every store holding a slot for the dead entity. Nothing read those slots — `has`, `get` and `entities` all skip non-live handles — so this was memory rather than a correctness bug, and `ComponentStore.prune()` existed as the interim sweep. The backlog framed the choice as per-store `remove` at `O(stores)` per destroy against a deferred sweep at `O(total entries)` per pass, and asked for the cost of each to be stated.
**Decision:** `World.destroyEntity` calls the new `ComponentRegistry.removeEntity(entity)` and then delegates to the allocator, in that order. The fan-out is synchronous and complete: after a destroy, no store holds a slot for that entity. `ComponentStore.prune()` stays, scoped to a store driven directly by an `EntityAllocator` with no `World` between them.
**Alternatives:** a deferred `prune()` sweep on a tick cadence, and a per-entity index of which stores hold it. **The sweep was rejected on invalidation timing rather than on cost**, and that is the load-bearing half of this decision: decision 0024 keys `QueryCache` on store `version`, so a sweep would bump the version of every store it touched on whichever tick it happened to run, and every cached query in the world would miss on that tick for a reason no system could point at. The eager fan-out moves the version exactly when the entity was destroyed. The entity→stores index was rejected because it costs a write per `set` to save a read per destroy, over a store count that is the number of *component types* and so is small and fixed.
**Consequences:** `destroyEntity` is now `O(stores)` rather than `O(1)`, which is the price, and it is bounded by a number that grows with the game's component vocabulary rather than with the world. **The order of the two lines is load-bearing and its failure mode is silent**: `ComponentStore.remove` refuses a dead or stale handle, so fanning out *after* the destroy makes every removal a no-op and reproduces exactly the leak this closes, with nothing failing — a destroyed entity's components are unreadable either way. `World.test.ts` asserts the mechanism, not only the outcome, and any future "clean up on destroy" work inherits the same trap. `ComponentRegistry`'s store map is now typed at a new `EntityScopedStore` rather than `unknown`, which is what lets `removeEntity` be written with no type assertion; that interface carries only `remove`, deliberately, and widening it for a save pass is BL-066.

## 0027 — Stores are enumerable through a value-erased read interface, and it has no `set` (2026-08-29)
**Status:** accepted
**Context:** BL-066. `ComponentRegistry` held one store per component and offered no way to walk them. Two callers need to: a save pass (`23`) serialising every store, and a debug overlay (`13`) counting entries; neither can do what `removeEntity` does, which is iterate the map from inside the class. BL-060's handoff recorded the obstacle as a language limitation — TypeScript has no existential types, so an enumerator whose element type mentions a component's `T` cannot be written, and every widening either loses the value type or forces an assertion at each call site.
**Decision:** `ComponentRegistry.stores(): IterableIterator<ErasedStore>`, where `ErasedStore` carries `def`, `size`, `version`, `get(entity): unknown` and `remove`. The registry's internal map is typed at `ErasedStore` rather than the narrower `EntityScopedStore` BL-060 introduced. **`set` is excluded and that exclusion is the decision**, not an omission to be tidied later.
**Alternatives:** (a) *the documented refusal* the backlog offered as the other acceptance path — say per-store access is by def only and tell a save pass to do something else. Rejected because there is nothing else it can do: it must reach every store, by definition. (b) *A per-store wrapper object* enforcing read-only at runtime rather than only in the type. Rejected because it allocates one object per store per enumeration and `06` bans allocation in per-frame paths — a debug overlay walks these every frame. (c) *Including `set`.* Rejected as unsound, below.
**Consequences:** The obstacle above is real and turned out **not to bind here**, for a reason worth generalising: neither caller reads `T`. A debug overlay counts; a serialiser copies an opaque value rather than branching on its type, because `04` §4.3 makes components plain serialisable data. So `unknown` is the honest type rather than a lossy one, every member of `ErasedStore` is *covariant* in `T`, and a `ComponentStore<T>` satisfies it structurally for every `T` with no assertion anywhere — the `as` count in `ComponentStore.ts` is unchanged at one. **`set` is the single contravariant member**, so an erased `set(entity, value: unknown)` would accept an `Owned` value into the `Transform` store with the compiler's blessing, undoing the `componentValue` brand one level up; two `@ts-expect-error` reads pin its absence so adding it breaks the build. The practical fallout lands on `23`: **a save pass can write itself out through this interface but cannot read itself back in through it**, so loading goes through `store(def)` with a real def and the load side needs a name-to-def table nothing owns yet — BL-067. Note also that the erasure is type-level only: the methods remain on the object and a caller who defeats the compiler reaches them, which is the trade alternative (b) names. Finally, **this does not solve BL-065**, which is the same widening one level down (`QueryCache.query` takes `ComponentDef<never>`, the bottom, where the fix is the top) and remains its own task.

## 0028 — The ECS module boundary sits at "what a component is" / "what a store holds" / "which stores exist" (2026-08-30)
**Status:** accepted
**Context:** BL-068. `ComponentStore.ts` had reached 631 lines against `CLAUDE.md`'s 500-line hard limit, holding four things: `ComponentDef`/`defineComponent`, the `Store`/`EntityScopedStore`/`ErasedStore` interfaces, the sparse-set `ComponentStore`, and `ComponentRegistry`. The backlog item named the registry as "the obvious seam" and left the rest open. A line count is a symptom, so the question was where the boundaries actually are, not where a knife makes three roughly equal pieces.
**Decision:** three files. `ComponentDef.ts` holds the *vocabulary* — the `componentValue` brand, `ComponentDef<T>`, `defineComponent`, and the three store interfaces — and mentions no storage layout. `ComponentStore.ts` holds one implementation of them, the sparse set. `ComponentRegistry.ts` holds which stores exist. The test file was split along the same three seams. No barrel file; the four consumers import from the specific modules.
**Alternatives:** (a) *the registry alone*, the item's own suggestion — a clean seam, and it leaves `ComponentStore.ts` at ~495 lines, five under the hard limit and still 65% over the soft one. Rejected because it satisfies the criterion by a margin that the next paragraph of prose erases, which is how the file got here. (b) *Splitting the sparse set from its own interfaces only*, leaving the registry where it is — rejected because the registry is the one part with a different *subject* (which stores exist, not what one holds), so it is the seam a reader would look for first. (c) *A shared test-fixture module* rather than repeating the four-line `Transform`/`Owned`/`at()` fixtures in each test file — rejected because it trades duplication a reader can see for indirection they must follow, on fixtures that are three lines and stable.
**Consequences:** the dependency direction is acyclic and one-way — registry → store → defs → allocator — so a second store implementation (a tag store with no values, a chunked one; `Store<T>`'s doc already anticipates one) drops in beside `ComponentStore.ts` without touching the vocabulary or the registry. **The comments moved with the code rather than being cut**, which the third acceptance criterion asked for and which is most of this file's length: it is the record of *why*, and losing it to a line count would be the wrong trade. One consequence of that: `ComponentRegistry`'s doc comments reference `ComponentStore.prune` and `.remove` for the reasoning behind an ordering and a cost, and those references now cross a file boundary. They are kept rather than inlined — the argument belongs with the method that embodies it, and duplicating it is how two copies drift. **The verification that matters for a move is the test count, not a green run**: unchanged at 342 pass / 0 fail, because content lost or duplicated in a mechanical split is invisible in a green suite but not in a count. **The limit is still unenforced**, which is the part this decision does *not* fix: `max-lines` would have caught the drift, and three test files outside this split are over the hard limit today, so enabling it is its own task (BL-069). Nine of the fourteen files over the *soft* limit are tests, so a rule scoped to sources only would enforce the limit precisely where it is not being broken.

## 0029 — The hard line limit is enforced by lint, at raw lines, on tests too; the soft one stays a convention (2026-09-01)
**Status:** accepted
**Context:** BL-069. `CLAUDE.md` has set files at 300 lines soft / 500 hard since the repository started, and nothing checked either. That is how `ComponentStore.ts` reached 631 and its test file 701 with no signal at any point (decision 0028). ESLint's built-in `max-lines` would have caught both, and BL-068 deliberately did not switch it on because three test files outside its split were over the hard limit and would have failed lint on files that task did not touch. BL-069's acceptance criteria offer an explicit either/or — enable the rule and get every file under it, or restate the limit as a convention nobody enforces and write down why — and require that the soft limit be decided too, and that test-file scope be stated rather than left implicit.
**Decision:** `max-lines` is on as an **`error` at 500**, applied to **every** TypeScript file including tests, counting **raw lines** (`skipComments: false`, `skipBlankLines: false`). `World.test.ts` (547), `EventBus.test.ts` (533) and `Rng.test.ts` (509) were split to satisfy it; none was exempted. The **soft limit of 300 is not enforced** and `CLAUDE.md` now says so in as many words — it is a convention, not a rule.
**Alternatives:** (a) *Scope the rule to sources only.* This was the tempting one and it is wrong for a measurable reason: **no source file is over 500** — the largest is `allocationHarness.ts` at 422 — so a sources-only rule turns on with zero code changes and enforces the limit precisely where nobody is breaking it. Nine of the fourteen files over the *soft* limit are tests, and all three over the *hard* limit were. A rule that cannot fail is not a rule. (b) *Enable with `skipComments` and `skipBlankLines`.* Both offenders' comment and blank density is high enough that either option drops all three under 500, closing BL-069 without moving a line of code. Rejected as dodging the question rather than answering it: a reader opening a 700-line file is not consoled by learning that 200 of them are comments, and in this repository — where decision 0028 explicitly chose to keep comments over line count — discounting them would invert that choice. (c) *A second `max-lines` at 300 on `warn` for the soft limit.* Rejected on BL-069's own criterion 2: lint runs in CI, where nobody reads warnings, so a warning is another number that reads like a rule and is not one. Fourteen files sit over 300 and every one is deliberate. (d) *Restate the hard limit as an unenforced convention too* — the criterion's other branch. Rejected because the limit has already failed once as an unenforced number, which is what BL-068 was.
**Consequences:** The three splits each cut at an existing `describe` seam, so no case moved between suites, and each pair shares a small fixture module (`World.testFixtures.ts`, `EventBus.testFixtures.ts`, `Rng.testFixtures.ts`) rather than duplicating fixtures. **That reverses decision 0028's alternative (c) and the reversal is deliberate, not an oversight**: 0028 rejected a shared fixture module for fixtures that were "three lines and stable", and preferred visible duplication to indirection. These are not that — `Rng`'s shared block is 113 lines of chi-square machinery whose critical values are stated rather than eyeballed, and two drifting copies of a statistical test is exactly what makes such a test worthless. The principle 0028 was applying (duplicate what is trivial, share what is substantial) is unchanged; only the size of the thing changed. **`Query.test.ts` is at 499, one line under the limit, and it is left there**: the next case anybody adds fails lint, which is the rule doing its job rather than a problem to pre-empt — and unlike before, the failure now says exactly what to do. **The soft limit is now honestly labelled.** It was previously indistinguishable in `CLAUDE.md` from the hard one, both rendered as numbers with no statement of which was checked; a reader had no way to learn that neither was. **The rule was verified to fire, not assumed to**: a 511-line probe file reports `File has too many lines (511). Maximum allowed is 500` and was then removed. The suite count is unchanged at 342 pass / 0 fail across 88 suites, which is the check that matters for a move (0028's own consequence, applied here).

## 0030 — Query signatures must be statically known, enforced by a limit rather than bounded by eviction (2026-09-04)
**Status:** accepted
**Context:** BL-063. `QueryCache` holds one entry per distinct component-set signature and never drops one. That is correct and bounded for the design `04` §4.3 describes — systems are a fixed list in `sim/systems/order.ts`, so the signature set is decided at authoring time — but nothing enforced it, and a signature built from *data* (a query per structure type, per crop species) would grow the map for the lifetime of the session, each entry holding an array as long as its result. The item's criteria offered an explicit either/or: an eviction policy, **or** `World.query` documented as accepting only statically-known signatures with something checking it — and, whichever was taken, the other named in a comment with why it was not.
**Decision:** the second. `query` accepts only statically-known signatures, and `SIGNATURE_LIMIT = 64` enforces it: a *new* signature past the limit throws, with a message naming the rule, the likely cause, the constant to raise, and this item. The limit is checked before the stores are resolved, so a refused query adds no entry and leaves the cache usable.
**Alternatives:** (a) *LRU on a cap.* Rejected on three grounds, the second being the one that decides it. It would be a guess — nothing in the repository builds a dynamic signature, so no caller's behaviour would size it, and `35` §3 forbids inventing a policy without one. **It would also make the cache slower in exactly the case it exists for**: decision 0024's version-keyed invalidation means a cached entry survives across ticks, and BL-059 measured the cold intersection at **1.00 ms** against **0.0784 ms** cached, so evicting a signature still in the system list converts a hit into a ~13x cold path against a 6 ms CPU budget. An LRU sized slightly too small thrashes; sized generously it never evicts, which is this limit with more moving parts. And there is no process-lifetime leak to fix: one `QueryCache` per `World`, constructed with it and unreachable from outside, so the map dies with the world — the real risk is growth *within* one session, which a limit addresses directly and eviction would hide behind a bounded-looking `size`. (b) *Drop-if-unqueried-for-N-ticks.* Same objections, plus it needs a tick number, and `QueryCache` deliberately observes no time — the "per-tick" in `04` §4.3 is about when results may be *reused*, which version keys answer without a clock. (c) *Documenting the rule with no check.* Rejected on the criterion's own wording ("and something checks it") and on precedent: the 300-line soft limit sat in `CLAUDE.md` unchecked from the first commit and was breached fourteen times (decision 0029). An unchecked rule in this repository has a measured track record.
**Consequences:** The limit is a **tripwire for a design error, not a capacity to tune**, and the error message says so — hitting it means a call site is assembling defs from content, and the fix is that call site, not the constant. 64 is reasoned rather than picked: `05` §1 lists thirteen system files, a handful of distinct queries each puts a fully populated Phase-6 game at order-50, while a content-derived signature passes 64 within one save file. **Failing loudly is this package's existing answer to exhaustion** — `EntityAllocator` refuses to alias when it runs out (BL-007 criterion 4) — and it is deterministic, so `sim/`'s hashability is untouched: the same call sequence throws at the same point in every build. **The boundary is pinned from below as well as above**, because an off-by-one that refused a build inside its stated budget would be worse than the unbounded map this started from: a test asserts 64 distinct signatures are accepted. **The check was verified able to fail rather than assumed to**, following 0029's precedent: deleting it fails three cases, weakening `>=` to `>` fails three, and changing the constant fails the case that pins its value in the message. Rejected because the name is doing real work at five use sites and, with a doc that says which position it is for, it is the place the reasoning lives.

**Status:** accepted

## 0034 — An allocation allowance is measured in samples, and the control asserts the gap rather than setting the boundary (2026-09-12)

**Status:** accepted
**Context:** BL-074 and BL-057, which are the same defect filed twice, four weeks apart, by two sessions that each measured it independently. `allocationAllowanceFromControl` returned `controlBytes / 100` and `measureAttributedAllocation` samples every 1024 bytes, so the allowance was a tolerance of **less than one sample** whenever the control read under 102 400. Measured 2026-09-12 on the CI container: the control reads **54 912 – 67 584 idle** and **77 280 – 101 952 under four allocating hog threads**, giving allowances of **549 – 1020** — 0.54 to 1.00 samples. The rule tolerated **zero** strays, and BL-065's two observed failures (`clamp` 1344 against 635.12; `stepSpring3` 1040 against 718.08) were each exactly one sample. The 1-in-20 was the rate at which a sample strayed, not a rate at which the allowance was unlucky. The harness's own comment called the factor of 100 "slack in the middle of a two-order-of-magnitude gap"; there was no slack, because the allowance sat under the quantum the instrument can report.
**Decision:** the allowance is `samplingInterval × MAX_STRAY_SAMPLES`, with `MAX_STRAY_SAMPLES = 4` — **independent of the control's magnitude**, which is BL-057's second criterion ("derived from the sampling interval rather than tuned") and BL-074's third ("the dependence on a control measured under the same contention is either removed or stated") taken on its *removed* branch. The control is still measured in the same process and still gates the run, but what it now establishes is the **gap**: `assertInstrumentResolvesControl` requires the control to reach 8× the allowance.
**The numbers 4 and 8 come from measurement, in sampling intervals, default options:**

| case | attributed | intervals |
|---|---|---|
| allocation-free operations — 130 readings, idle and under 4 hog threads | **0** | 0 |
| worst stray ever observed (BL-065, real full-suite load) | 1344 | 1.3 |
| one allocation per 10 000 calls | 0 – 3200 | 0 – 3.1 |
| one allocation per 1000 calls | 4224 – 11 648 | 4.1 – 11.4 |
| **one per call** — the control | 54 912 – 101 952 | **53.6 – 99.6** |

Four intervals sits 3× above the worst observed stray and 13× below the weakest control, with every allocation-free reading at **zero** rather than merely under the bound. Eight is the ratio the control actually clears by 13–25×, left loose enough for a slower machine.
**Alternatives:** (a) *Raise the factor of 100.* Rejected on the item's own instruction and on the arithmetic: a larger hundredth is still a hundredth, still moves with a control that reads low exactly when the machine is contended, and still says nothing about the sample granularity that causes the failure. Raising the constant "without saying what the new number is a hundredth *of* would repeat the mistake at a larger size". (b) *Delete the control.* Rejected — BL-050's first dead end was a harness whose signal was always zero, which passes every case including the ones that should fail, and a constant threshold cannot tell "this operation allocates nothing" from "the profiler recorded nothing". The control is the only thing that rules that out, which is why it kept a job rather than losing one. (c) *Keep `repeats: 6` as the fix,* which is what BL-006 did locally in `EventBus.queued.test.ts`. Rejected because it is a mitigation whose own comment called it "a local patch, not the fix": it makes a stray have to recur in all six passes rather than making the boundary correct, it doubles that file's runtime, and leaving it in would mean that file kept passing for the old reason and never exercised this change. It was removed. (d) *A boundary that also catches a sparse allocator.* Not available at this granularity — one allocation per 1000 calls reads 4224–11 648, whose bottom is a hair above four intervals — and pursuing it by moving this constant goes the wrong way in one direction and re-creates BL-074 in the other. Filed as **BL-078**.
**Consequences:** The gap assertion is what makes "do not raise the allowance blindly" **enforceable rather than advisory**, and that was measured rather than hoped: with `MAX_STRAY_SAMPLES` at 6 the suite is green and at 8 the guard fires, so on this container the control backs at most 6 intervals and the boundary **cannot** be widened toward the control without the run going red. That is a stronger property than the old derived allowance had, which by construction could never fail this way — a hundredth of the control is a hundredth of it however small it gets. **Criterion 2 is a permanent test, not a perturbation**: a deliberate per-call allocator runs through `assertNoAllocation` itself and is asserted to be rejected, following BL-069's and BL-063's precedent, and the two readings that actually failed (1344 and 1040) are pinned as numbers so nobody re-derives the old rule. The cost: `allocationHarness.ts` is now **496 of its 500 allowed lines**, so the next thing added to it needs a seam rather than a paragraph — decision 0029's situation again, and the tables above live here partly for that reason. **The instrument guard is stricter than what it replaced** (8 × 4096 = 32 768 against the old 10 000 floor), which is deliberate and is the trade for a fixed allowance; a machine whose control reads below 32 768 now fails loudly where it used to produce a small allowance and a green run.

**The experiment came before the decision, and it is the whole reason the decision is this one.** BL-081's notes were explicit that a session would get this wrong from first principles: `register()` must run in the main thread before the first aliased import while the hook itself runs on a loader thread, so whether a `.ts` loader hook can register itself while Node is stripping its types is a question about module-loading order. **Run rather than reasoned, on Node v22.22.2: it works, 369/369.** Had it not, `allowJs` was the only route and the decision would have narrowed to `checkJs` or not.
**Alternatives:** (a) *`allowJs` alone.* Rejected: it buys syntax checking and inference and no annotations, so the four `TS7006` errors below would still be invisible — a gate that reports nothing is the shape of defect this item exists to stop repeating. (b) *`allowJs` + `checkJs`.* Real checking, but it makes **JSDoc load-bearing** in a repository whose every other file expresses types in the language, and it opens the door to more JavaScript rather than closing it. Rejected on the same ground as (a)'s weaker sibling: the answer that leaves two languages in the tree is the answer that has to be re-litigated. (c) *Deliberately neither.* Rejected outright — it is the status quo, and the status quo is the four-item pattern above. (d) *Convert `eslint.config.js` too.* Rejected, and this is the one that needed a real trade rather than a preference: ESLint v9 reads `eslint.config.ts` only through `jiti`, a **runtime dependency of the lint step** that `35` §4 puts behind justification, for a file that configures the linter, ships nowhere, and is loaded by ESLint rather than by Node. The exemption is cheaper than the dependency, and making it a checked list of exactly one is what keeps it from becoming a habit.
**Consequences:** **Turning `tsc` on the two files found four real errors on the first pass** — every parameter of the `resolve` hook was an implicit `any` (`TS7006`), now typed through Node's own `ResolveHook` from `node:module`. That is BL-080's finding arriving again on schedule and is the third consecutive time a first check of an unchecked file has found something. The runtime evidence is the suite itself: 369 tests load through these files, and they pass. **Confirmed able to fail before being trusted green**, as 0033, 0035 and 0036 were: a bad annotation in `aliasResolver.ts` reports `TS2322` and a bad argument in `registerAliases.ts` reports `TS2769`, both failing `pnpm typecheck`; and four controls each break exactly one assertion of the new guard — a new `tools/*.mjs` fails both new cases, a stray `packages/**/*.js` fails the first, a stale exemption entry fails the first, and dropping `--import` from `test:node` fails the second. **The guard reads `git ls-files` rather than walking the tree**: that is exactly "files a person wrote and committed", so generated output is excluded by the same rule that excludes it from review and there is no second ignore list to drift; the cost is that it needs a git checkout and throws in a source tarball, which is the safer of the two failures for a guard. Cost worth naming: `eslint.config.js`'s `disableTypeChecked` block still lists `tools/**/*.ts` and still says those files "are not members of any TypeScript project", which **stopped being true at 0036** and is now one item further out of date — filed as **BL-082** rather than fixed here, because switching type-aware lint rules on over `tools/` is a change with its own findings and its own size.


## 0038 — The type-aware lint rules run over `tools/`; the lint *fixtures* are the part that must stay exempt (2026-09-21)

## 0039 — A second fixture directory, inverted on exactly one axis from the first (2026-09-23)

**Status:** accepted
**Context:** BL-083, filed by 0038 with its complication already measured. `tools/check-lint-rules.ts` proves the four custom `no-restricted-syntax` rules fire by linting deliberate violations in `tools/lint-fixtures/`. Nothing did the same for the *type-aware* rules that 0038 switched back on over `tools/`, and that gap is silent in the worst way: measured under a restored `tools/**/*.ts` entry in `disableTypeChecked`, `pnpm lint` exits 0, `pnpm typecheck` exits 0, `pnpm test` is 372/372, and the only difference anywhere is that an entire class of rule has stopped reporting. **`tools/lint-fixtures/` cannot host the fixture that closes it**, by 0038's own decision: that directory is in the `disableTypeChecked` block and outside `tools/tsconfig.json`'s `include`, so under type-aware settings its files do not parse.
**Decision:** a second fixture directory, **`tools/type-aware-fixtures/`**, which is the inverse of the first on exactly one axis — it is in ESLint's `ignores` (so `pnpm lint` stays green on a deliberate violation) and in **neither** the `disableTypeChecked` block **nor** `tools/tsconfig.json`'s `exclude`. One file in it, violating `@typescript-eslint/no-unnecessary-condition`, plus a fifth row in `check-lint-rules.ts`'s `EXPECTATIONS`. `tools/tsconfig.json` needed no edit: its `include` is already `"**/*.ts"` and only `lint-fixtures` is excluded, so the new directory is type-checked by construction — **the third consecutive item whose predicted configuration change turned out to be zero** (0037, 0038, this).
**The assertion is keyed on the rule id, and that is the load-bearing detail.** A fixture is only evidence if nothing *else* can satisfy the expectation. `no-unnecessary-condition` is undecidable from syntax — it has to know that `value` is a `string` — so a syntactic rule reporting on the same file cannot stand in for it, which is BL-083's third criterion. Measured rather than argued: under the restored block, ESLint reports **zero** messages of any kind on the fixture, so nothing masks the regression.
**And it rehabilitates the control 0038 recorded as a miss.** 0038 tried a `no-unnecessary-condition` probe, got `no-inferrable-types` — a stylistic rule that was never off — and correctly counted it as proving nothing. The rule was not the problem; **the shape of the violation was**. An annotated initializer attracts a stylistic rule first; a comparison against `undefined` on a non-nullable type attracts only the type-aware one. A control that fails for the wrong reason is fixed by changing the probe, not by abandoning the rule.
**Alternatives:** (a) *Put the assertion in a `tools/*.test.ts` so `pnpm test` runs it.* The criterion allows either, and `pnpm test` is in the verify block where `pnpm lint:rules` is only in the prose beneath it. Rejected for this task because BL-083's own notes name `EXPECTATIONS` as the home and the table already carries four siblings, so splitting the family across two runners to buy one gate would cost more than it buys — but the exposure is real and is filed as **BL-084** rather than waved away. (b) *Chain `pnpm lint:rules` into `pnpm lint`,* which is how 0033 and 0035 made `format:check` unskippable. **Rejected on BL-079's finding 1: a guard cannot live inside the thing it guards.** `lint:rules` exists to catch a bad `eslint.config.js`, and an edit that breaks the lint config would take the guard down with it. (c) *Widen `tools/lint-fixtures/` to hold both kinds.* Rejected — it is exempt for a reason that is still exactly true, and 0038's finding was that one glob covering two populations for one stated reason is what caused the original defect. (d) *Assert on the config file's text instead of on ESLint's behaviour.* Rejected: it would pass on a config that parses the way it reads and behaves differently, which is the class of bug this whole family of gates exists to catch.
**Consequences:** the repository now has two fixture directories whose exemptions must not be confused, and the top of `eslint.config.js` says which is which and how to choose. A new fixture goes in the one matching the rule it proves; putting a type-aware fixture in the syntactic directory makes it report nothing, and `pnpm lint:rules` says so. **Confirmed able to fail before being trusted green**, as 0033, 0035, 0036, 0037 and 0038 were: with `tools/**/*.ts` returned to the block the new row reports 0 while the four existing rows stay green, and reverting restores 5/5. What is still not checked is one level up and is **BL-084**: nothing automatic runs `pnpm lint:rules` at all, so all five rows depend on a session typing it until **BL-019** brings up CI.
